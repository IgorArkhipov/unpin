# Unpin v1.4.2 release workflow recovery

## Summary

Ship a patch release that makes the tag-triggered release workflow safe to rerun after a GitHub release has already been published. Existing drafts continue to refresh only after the provider-evidence guard passes, missing releases continue to create drafts, and published releases become an explicit non-mutating success path.

## Context

The `v1.4.1` tag workflow built, signed, attested, and uploaded all platform artifacts successfully. GitHub returned HTTP 503 while the final draft-release job was running. The release was later verified and published, but rerunning the failed job cannot recover the workflow because `.github/workflows/release.yml` currently requires every existing release to have `isDraft == true`.

This is a workflow-state defect, not a product-runtime defect. The patch must preserve the repository's release safety contract: provider-matrix evidence attached to a draft must never be silently replaced, and an already-published immutable release must never be mutated by a rerun.

## Settled decisions

- Prepare and ship `v1.4.2` instead of accepting the incident-era red run or rerunning a job known to fail deterministically. This was selected by the maintainer after the alternatives and consequences were presented in this session.
- Treat an existing published release as an intentional no-op success. The workflow may inspect its state and tag identity, but must not upload, clobber, edit, or recreate release assets.
- Retain the current behavior for missing releases and existing drafts, including the provider-evidence rejection before any draft refresh.
- Keep this delivery-focused: no Rust behavior changes, dependency changes, or unrelated release refactors.

## Implementation

### 1. Make release reconciliation state-aware

Update `.github/workflows/release.yml` so the final release step performs one
authenticated REST lookup with bounded retries, classifies its HTTP status,
and validates the returned `draft`, `immutable`, and `tag_name` fields.

- Existing draft: require it to be mutable, reject provider-matrix evidence already attached to the draft, then upload with `--clobber` as today.
- Existing published release: require the repository's published-release invariant (`isImmutable == true`), emit a clear notice, and exit successfully without any mutation.
- Confirmed HTTP 404: create a draft or draft prerelease as today.
- Transport, authentication, rate-limit, and server failures: retry when safe,
  then fail without attempting release creation.
- Malformed or contradictory state: fail closed with expected and actual values.

### 2. Add regression coverage and operator documentation

Extend `scripts/test_release_workflow.py` with structural assertions and
executable fake-API/fake-CLI scenarios. The tests must prove that draft upload
remains inside the draft-only branch, the published branch checks immutability
and contains no release mutation command, only HTTP 404 creates a draft, and
transport or non-404 HTTP failures do not invoke `gh`.

Update `docs/RELEASING.md` to distinguish the two rerun boundaries:

- Before publication, a draft containing provider evidence still refuses refresh.
- After publication, an immutable release causes a safe no-op success.

### 3. Prepare the patch release

Bump all repository-owned version surfaces from `1.4.1` to `1.4.2`:

- `Cargo.toml`, `Cargo.lock`, and `crates/unpin-core/Cargo.toml`
- `apps/unpin-desktop/UnpinDesktop.xcodeproj/project.pbxproj`
- current-version examples in `README.md` and `docs/DESKTOP.md`
- `CHANGELOG.md`
- new `docs/releases/v1.4.2.md`

The release note will describe the workflow recovery and state that this patch changes delivery automation only.

## Verification

Run the narrow checks first:

1. `python3 -m unittest scripts.test_release_workflow`
2. `python3 -m unittest scripts.test_check_release_assets`
3. workflow YAML parse/lint through the repository's existing test or hook path
4. `cargo metadata --locked --no-deps`
5. `cargo run -p unpin-cli --locked -- --version`
6. `git diff --check`

Because this release changes no program logic, use the documented maintainer-approved delivery-only exception rather than rerunning the full provider matrix. Before tagging, require focused release evidence: workflow tests, locked metadata, version smoke, the normal PR checks, and a clean merge commit on `main`. Git hooks remain responsible for Trunk; do not run Trunk directly.

## Review and delivery

1. Review the workflow state machine, regression assertions, release metadata, and documentation as one scoped PR.
2. Push `release/v1.4.2`, open the PR, address validated review feedback, and wait for required checks.
3. Merge only when GitHub reports the PR mergeable, required checks are green, and no review threads remain unresolved.
4. Fast-forward local `main`, tag the exact merge commit as `v1.4.2`, and push the tag.
5. Watch the release workflow through draft creation, perform the delivery-only release verification described in `docs/RELEASING.md`, publish the draft, and verify the immutable public release, checksums, attestations, and latest-release pointer.

## Risks and mitigations

- A loose published-state check could hide a mutable or mismatched release. Validate tag identity and immutability and fail closed for unexpected values.
- Moving the upload branch could weaken the provider-evidence guard. Keep that guard immediately before draft upload and cover its ordering in the workflow test.
- Version drift across Rust, desktop, docs, and lockfile surfaces could produce mismatched artifacts. Use the same version file set as the `v1.4.1` release commit and verify locked metadata plus CLI version output.
- GitHub incident recurrence could cause transient CI or release failures. Preserve evidence, retry only failed transient operations, and never change release state to work around an outage.
